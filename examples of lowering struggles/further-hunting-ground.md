# Further hunting ground

Do not restrict this research to languages that resemble Idriç.

The phenomenon is broader:

> code that writes code chooses a representation, and that choice can accidentally destroy a structure the generated program needed.

## Ruby / language VMs

Search:

- ruby-core / public-inbox;
- old YARV material;
- LuaJIT mailing lists and Mike Pall discussions;
- PyPy developer archives;
- HotSpot/OpenJDK compiler-dev;
- V8 design discussions;
- Self and Strongtalk archives;
- Smalltalk VM work.

Look for:

- stack versus register bytecode;
- superinstructions;
- branch fusion;
- JIT IR redesign;
- code size explosions;
- deoptimization information being lost;
- tracing versus method JIT representation fights.

## Databases and query compilers

SQLite is only the beginning.

Search:

- PostgreSQL hackers;
- DuckDB;
- MonetDB;
- HyPer/Umbra discussions where public;
- ClickHouse;
- database JIT/code-generation systems.

Look for:

- query flattening that loses ordering or cardinality information;
- expression compilation duplicating work;
- generated bytecode or LLVM IR becoming enormous;
- optimizer decisions that are locally reasonable but generate terrible execution programs.

## Parser and lexer generators

Search:

- GNU Bison;
- yacc descendants;
- ANTLR developer lists;
- Ragel;
- re2c;
- parser-combinator compilers;
- PEG/packrat generators.

Potential failure modes:

- state explosion;
- table versus code generation;
- duplicated semantic actions;
- loss of grammar structure after automaton conversion;
- generated source too large for the host compiler;
- optimizer-hostile generated switch forests.

## Regex engines and automata generators

Search:

- PCRE/PCRE2;
- RE2;
- Hyperscan;
- TRE;
- old grep/egrep implementation discussions.

The same structure question appears when:

```text
regular expression
    ↓
NFA / DFA / bytecode / native code
```

A representation may make matching fast while exploding code/state size.

## Hardware and HDL generators

Search:

- Chisel;
- Clash;
- Bluespec;
- FIRRTL;
- MLIR hardware dialects;
- HLS tools;
- FPGA mailing lists.

The analog of our shader problem may be particularly sharp here: a source-level conditional can become multiplexers, duplicated logic, predication, or sequential control depending on when and how it is lowered.

## Template and source-to-source generators

Search for systems that generate C/C++:

- SWIG;
- protobuf/thrift generators;
- RPC stub generators;
- numerical kernel generators;
- Halide;
- FFTW;
- ATLAS;
- SPIRAL;
- polyhedral code generators.

Generated code often fails because it is technically correct but hostile to the next compiler.

## Archives to mine

High-value archives include:

- `comp.compilers`;
- MarkMail mirrors;
- public-inbox archives;
- mail-archive.com;
- project-specific Pipermail archives;
- Google Groups mirrors of old lists/Usenet;
- old bug trackers;
- conference/workshop proceedings with implementation notes;
- developer blogs written during rewrites rather than after them.

Do not rely on one keyword vocabulary. Search by project and then read around concrete developer complaints.

## What to save locally

For high-value examples, preserve:

1. canonical URL;
2. archive URL or Wayback fallback if fragile;
3. date and participants;
4. tiny schematic reproducer written in our own words;
5. representation before;
6. lowering step;
7. bad generated structure;
8. attempted fixes;
9. final/current design, if known;
10. what Idriç might learn from it.

When licensing permits, also preserve exact API definitions or small reference programs locally so future work is not dependent on a moving external page.

## Search stopping rule

For each ecosystem, stop after either:

- finding one genuinely new failure mechanism; or
- reading several serious implementation discussions that only repeat mechanisms already in this folder.

The goal is not exhaustive compiler history. The goal is a diverse collection of **different ways generators lose structure**.
