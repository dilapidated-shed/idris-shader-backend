# SQLite / VDBE

SQLite belongs here because it is a mature program generator: SQL is analyzed and turned into a VDBE bytecode program.

The interesting design choice is that SQLite tries to do most optimization **before** VDBE bytecode generation.

## Why bytecode comes late

Richard Hipp explains that most optimization occurs on the AST before bytecode generation, and that generated bytecode is only rarely rewritten afterward.

Source:

- https://sqlite.org/forum/forumpost/93f9bfcec0

That is already a useful architectural contrast with our old shader recovery pass.

The SQLite approach is approximately:

```text
SQL structure
   ↓
AST / planner optimization
   ↓
chosen plan
   ↓
VDBE program
```

rather than generating a bad low-level program and relying on a heroic bytecode optimizer to rediscover the SQL structure.

## Planner choice can still generate disastrous bytecode

A 2021 regression involving `OP_SeekScan` produced queries hundreds of times slower in a distilled test. High-level query plans could look similar while opcode-level output differed materially.

Source:

- https://sqlite.org/forum/forumpost/8c53a4c826e1bd8d

The discussion is valuable because equivalent-looking SQL spellings gave the planner different freedom and therefore produced very different VDBE programs.

The bug was not "VDBE is bad." It was that a planning/lowering decision created a bad execution program.

## AST corruption can become wrong bytecode

A 2023 SQLite bug is even more direct: an optimization set one field in the SQL parser/AST structure incorrectly, and the result was incorrect generated bytecode and an incorrect answer.

Source:

- https://sqlite.org/forum/info/a68313d0545273c8

This is the generator pipeline in its simplest dangerous form:

```text
bad structural annotation
        ↓
bad lowering decision
        ↓
wrong generated program
```

## "Obvious" structural optimization can break 1,524 tests

A discussion about removing apparently unnecessary `ORDER BY` clauses from subqueries is exactly the kind of developer struggle this notebook wants.

The transformation looked simple. Trying it produced 1,524 test failures. The thread then works through hidden dependencies on ordering, aggregate behavior, historical behavior, user expectations, and the exact conditions under which the optimization can safely apply.

Source:

- https://www.sqlite.org/forum/info/6be1468b8548b2d1d

The lesson is broader than SQL:

> structure that appears semantically redundant to one phase may carry operational or compatibility information relied upon elsewhere.

## Generated C has generator problems too

SQLite also contains tooling that rewrites the generated/hand-maintained VDBE interpreter C so that local variables for individual opcodes share a union, reducing stack usage and helping the C compiler generate better code.

Reference implementation:

- `tool/vdbe-compress.tcl` in SQLite source trees.

This is another level of generation:

```text
SQL
  -> VDBE bytecode
  -> VDBE interpreter behavior

and separately

opcode implementation source
  -> transformed C
  -> C compiler
  -> machine code
```

Every layer can introduce or destroy structure.

## Why SQLite is useful here

SQLite broadens the question from "compiler IR" to "program generators":

- planner structure;
- execution-plan structure;
- generated bytecode;
- generated/interpreted C;
- and later machine code.

It is an excellent place to hunt for cases where a generator made a locally convenient choice that produced a globally terrible program.
