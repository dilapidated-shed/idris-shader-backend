# Examples of lowering struggles

This folder is about a broad failure pattern:

> a program generator has a useful structure, lowers it into something more convenient, and later discovers that the lowering destroyed information that mattered.

The motivating shader example is `RSelect`: source `if / then / else` became two already-computed values plus a final select. That made it possible to generate work from both branches and then choose only the result. A later pass had to reconstruct the control-flow structure that had already been erased.

The point of this folder is **not** to collect polished modern IRs. It is to collect evidence of the struggle that produced them.

Useful artifacts include:

- mailing-list arguments;
- reverted compiler changes;
- bugs caused by code motion or speculation;
- developers describing why one IR made another phase impossible;
- code generators that explode source structure into huge generated programs;
- cases where a lower-level representation made later optimization harder;
- cases where a target-specific representation leaked upward too early;
- and designs where a later compiler phase had to rediscover structure that an earlier phase threw away.

## Questions to ask

For every example:

1. What useful structure existed originally?
2. Which lowering destroyed or blurred it?
3. What bad generated program resulted?
4. Was the failure correctness, work duplication, code size, evaluation order, compile time, or target quality?
5. Did the authors reconstruct the structure later, preserve it longer, add annotations, or change the IR?
6. Which choices were tried and rejected?
7. Could Idriç make the problematic transformation structurally impossible?

## Current examples

- [LLVM](llvm.md): branch/select/speculation/if-conversion repeatedly crossing the wrong boundary.
- [STG and GHC](stg-ghc.md): laziness, `case`, join points, floating, and evaluation-order mistakes.
- [Idris](idris.md): useful negative and positive examples from the compiler family we are actually consuming.
- [MLIR](mlir.md): structured regions as a current answer, plus arguments about whether regions were the right answer.
- [WebAssembly](webassembly.md): deliberate structured control flow despite pressure from compiler writers for arbitrary CFGs.
- [Cranelift](cranelift.md): EBB cleanup, block parameters, and explicit concern about computations being forced before branches.
- [GCC / GIMPLE](gcc-gimple.md): a particularly clean case where `?:` is first expanded into control flow and only reintroduced later if appropriate.
- [Ruby / YARV](ruby-yarv.md): VM instruction-set redesign, superinstructions, compare+branch fusion, and the cost of choosing stack versus register-transfer representations.
- [SQLite / VDBE](sqlite-vdbe.md): query/compiler structure, generated bytecode, planner choices, and why optimization happens before bytecode emission.
- [comp.compilers](comp-compilers.md): old practitioner discussions about IR design, invalidated analysis, code generation, and bad lowering boundaries.
- [Further hunting ground](further-hunting-ground.md): parser generators, regex engines, JITs, query planners, HDL/code generators, template/code generators, and obscure languages.

## Working hypothesis

For Idriç, preserve the semantic operation first:

```text
if condition
then computation A
else computation B
```

Only later should a target be allowed to prove that flattening is safe and useful:

```text
structured conditional
        |
        +-- branch
        +-- select / cmov
        +-- predication / masks
        +-- target-specific lowering
```

This is a hypothesis to test against historical failures, not a conclusion to assume.
